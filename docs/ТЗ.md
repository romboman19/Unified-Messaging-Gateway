## 3. Problem statement

There are separate transport components:

- built-in DBLtek GoIP SMS Server for GSM/SMS;
- UnoAPI Cloud for unofficial WhatsApp integration via Baileys;
- `signal-cli-rest-api` for Signal.

Each solves only its own part and has its own API, event format, configuration, statuses and data storage. The built-in GoIP SMS Server is functionally adequate, but its web UI, alerts, integrations, handling of concatenated SMS and overall management model are outdated.

A single modern internal service is required where the administrator, through the web UI, can:

- add and configure channels;
- connect multiple WhatsApp and Signal numbers;
- manage the four SIM cards of a GoIP-4 separately;
- test sending and receiving;
- see history, statuses and errors;
- configure event routing;
- configure HTTP webhook, email, Telegram and other destinations;
- control queues, retries and undelivered events;
- check SIM balance via USSD;
- receive low-balance and health alerts;
- use a single external API.

The main operator correspondence may happen in Chatwoot or another system. UMG is a transport, service and administrative gateway, not a replacement for a full contact centre.

## 5. Key decisions

| ID | Decision |
|---|---|
| ADR-001 | System is a modular monolith with a separate worker, not a set of microservices. |
| ADR-002 | UnoAPI, Signal API and DBLtek SMS Server are not embedded into core code; they run as separate transport services/sidecars. |
| ADR-003 | Primary GoIP transport for release 1.0 is an adapter to the built-in DBLtek SMS Server v1.30.1. |
| ADR-004 | Direct GoIP UDP server is not required for release 1.0; it is created only as a separate future adapter after conformance tests. |
| ADR-005 | Core is the single source of truth for messages, routes, events, statuses and alerts. |
| ADR-006 | PostgreSQL is source of truth; Redis must not be the only place for important state. |
| ADR-007 | All external deliveries have at-least-once semantics; duplication is neutralised by idempotency and deduplication. |
| ADR-008 | Chatwoot has no special module in release 1.0. It integrates via generic webhook and the single send API. |
| ADR-009 | All ordinary channel, endpoint, webhook, alert, balance and retention settings are configured through the UI. |
| ADR-010 | Docker image updates, emergency password reset and infrastructure actions remain operational commands, not UI functions. |
| ADR-011 | Interface and user messages are in Ukrainian only. |
| ADR-012 | In release 1.0 there is no automatic switching to another channel on failure. The same channel and endpoint are retried. |
| ADR-013 | An outbound message has a maximum of 3 total attempts: immediately, after 60 seconds, then another 60 seconds. |
| ADR-014 | Absence of a delivery receipt alone is not a reason to resend, to avoid duplicates. |
| ADR-015 | Text messages are retained indefinitely; attachments have configurable retention. |
| ADR-016 | Canonical phone format is stored as E.164; output/sending format is configured separately. |
| ADR-017 | LLM is used only as a fallback for parsing complex USSD responses after deterministic rules. |

## 6. Transport component analysis

### 6.1. UnoAPI Cloud

Source: `https://github.com/clairton/unoapi-cloud`

At the time of analysis the repository:

- implements unofficial WhatsApp API via Baileys;
- supports multi-device and multiple sessions;
- uses an API format close to WhatsApp Cloud API;
- has QR pairing, webhook events, message statuses;
- supports text, media, contacts, groups and interactive messages;
- can store media in filesystem, S3-compatible storage or Redis;
- has simple/standalone/web/worker/cloud modes;
- supports Redis and RabbitMQ;
- has its own retry/dead-queue mechanisms;
- has `/ping` for health;
- is GPL-3.0 licensed;
- checked package metadata: `2.11.2`, Node.js `>=24`.

**Decision for UMG**

- Run UnoAPI as a separate container.
- Do not copy its GPL code into proprietary/core modules.
- Do not publish UnoAPI port on the LAN; access only from the private Docker network.
- All webhooks from UnoAPI are received by UMG, stored and normalised.
- Media files are copied to UMG local storage; UMG does not rely on UnoAPI retention.
- Image MUST be pinned to exact tag + digest; `latest` is forbidden in production.
- UnoAPI updates are performed only after smoke/contract tests.
- UMG UI must hide the technical UnoAPI interface.

**Risk**

UnoAPI uses an unofficial WhatsApp protocol. Possible issues include Baileys/WhatsApp changes, session drops, temporary incompatibility, number blocking, and the need to update the transport image quickly. This risk must be visible in the dashboard and documentation.

### 6.2. `signal-cli-rest-api`

Source: `https://github.com/bbernhard/signal-cli-rest-api`

The component:

- is a Dockerized REST API around `signal-cli`;
- supports number registration and verification;
- supports linked device via QR;
- has `/v2/send`;
- supports attachments;
- supports groups, reactions, receipts, quoting, contacts, profiles and other operations;
- has `/v1/health`;
- supports multiple accounts;
- in `json-rpc` mode keeps one daemon process and is faster than launching the JVM per request;
- in `json-rpc` mode can forward receive events to `RECEIVE_WEBHOOK_URL`;
- stores keys and registration in a persistent volume;
- has MIT license.

**Decision for UMG**

- Use `MODE=json-rpc` as the main stable mode.
- `json-rpc-native` MAY be tested separately but must not be production default without soak test.
- Container is not published on the LAN.
- Signal persistent volume is a critical secret backup asset.
- Receive webhook is directed to a private UMG callback.
- Because the receive webhook transport does not provide full authorisation/queuing from the wrapper side, the callback is only available on the private Docker network with an unguessable path token.
- UMG must acknowledge the callback only after reliably recording the event.
- UMG itself performs fan-out, retries and DLQ.
- UI must show trust identity, rate limit/captcha and account disconnection issues.

### 6.3. DBLtek GoIP SMS Server

Sources:

- `http://dbltek.com/update/goip_install-v1.30.1.tar.gz`
- `http://static.dbltek.com/SMS+SERVER+API+%282%29-aidlnBqmKioSRqiilimiplq.pdf`
- `http://static.dbltek.com/SMS+Server+Installation+Guide-20210630-aidlpBqmKioSRpinijimplq.pdf`

Official DBLtek page still publishes SMS Server v1.30.1, API Doc and User Manual.

API documentation v1.27+ describes:

- HTTP + JSON;
- UTF-8;
- mandatory auth section;
- `sendsms`;
- `querysms`;
- `querylines`;
- status callback for outbound SMS;
- callback for inbound SMS;
- line identifiers;
- states `ACCEPT`, `REJECT`, `sending`, `unsend`, `succeeded`, `failed`;
- `taskID`;
- `err_code`;
- line health `online`, `reg`, `remain_sms`, `day_remain_sms`.

Expected JSON endpoints:

- `POST /goip/sendsms/`
- `POST /goip/querysms/`
- `POST /goip/querylines/`

Example send payload:

```json
{
  "auth": {
    "username": "login",
    "password": "password"
  },
  "goip_line": "G101",
  "number": "380XXXXXXXXX",
  "content": "Тестове повідомлення"
}
```

Expected response:

```json
{ "result": "ACCEPT", "taskID": "5689" }
```

or:

```json
{ "result": "REJECT", "reason": "none_line" }
```

Expected status callback:

```json
{
  "taskID": "5689.380XXXXXXXXX",
  "goip_line": "G101",
  "send": "failed",
  "err_code": "350"
}
```

Expected inbound SMS callback:

```json
{
  "goip_line": "G101",
  "from_number": "380XXXXXXXXX",
  "content": "Текст SMS",
  "recv_time": "2026-07-29 21:00:00"
}
```

The old compatibility API also uses `dosend.php` and form/query fields, including `goipname`, `smsnum`, `Memo`. It should only be used as a fallback profile.

**Important limitation**

The original v1.30.1 archive was not unpacked during preparation of this specification. Before writing a production adapter the agent MUST conduct Phase 0 discovery on the real archive and live server:

- record the SHA-256 of the archive;
- determine exact runtime dependencies;
- record real URL, method, content type and response codes;
- check for CSRF/session requirements;
- check callback payloads;
- check USSD endpoints;
- check DB schema only as a fallback compatibility path;
- check multipart metadata;
- create replay fixtures and contract tests.

**Architectural decision for GoIP**

UMG MUST support two production-safe modes of one adapter:

- `goip_vendor_remote` — connect to an existing separate DBLtek SMS Server via API. This is the first mode for development and canary.
- `goip_vendor_embedded` — DBLtek SMS Server runs in a private compatibility container/sidecar in the same Docker Compose. The archive is provided by the system owner and is not committed to the public repository.

Future third mode:

- `goip_native_udp` — own implementation of the GoIP UDP protocol. Not required for release 1.0.

### 6.4. Native GoIP protocol — future adapter only

Available protocol documentation describes:

- clear-text UDP;
- need for retransmission;
- keepalive approximately every 30 seconds;
- ID/password authentication;
- receiving SMS with ACK;
- statuses;
- USSD;
- separate management commands.

Because of clear-text UDP and the need to implement reliability yourself, this mode should not be mixed with core. If implemented:

- it is a separate adapter package/process;
- UDP 44444 is allowed by firewall only from the GoIP IP;
- replay/deduplication is mandatory;
- transport credentials are not logged;
- conformance test compares behaviour with the built-in server;
- managing one GoIP line simultaneously by the vendor server and the native adapter is forbidden.

## 10. Statuses and state machine

### 10.1. Canonical statuses

Outbound: `created`, `scheduled`, `queued`, `dispatching`, `accepted`, `sent`, `delivered`, `read`, `failed`, `cancelled`, `expired`, `unknown`.

Inbound: `received`, `assembling`, `incomplete`, `processed`, `forwarded`, `forward_failed`.

### 10.2. Semantics

- `accepted` — transport accepted the request but has not yet confirmed sending.
- `sent` — transport/operator confirmed sending.
- `delivered` — there is a separate delivery receipt.
- `read` — there is a read receipt.

For SMS via DBLtek, `succeeded` defaults to `sent`, not `delivered`.

DBLtek field `receipt=1` per documentation means a response from the subscriber, not a guaranteed network delivery receipt. It is stored as metadata/event but not automatically mapped to `delivered`.

### 10.3. Resending

Resending is allowed only when:

- transport request was not accepted;
- a retryable error was returned;
- an asynchronous status `failed` is classified as retryable.

Do not automatically resend when:

- transport already returned `accepted/sent`;
- delivery/read status has simply not arrived yet;
- result is `unknown` but there is a risk the message was actually sent.

For `unknown` the system:

- sets status `unknown`;
- creates an alert;
- allows manual retry with a warning about duplicate risk.

### 10.4. Message retry policy

Default:

- `max_attempts = 3` total;
- attempt 1: immediately;
- attempt 2: after 60 seconds;
- attempt 3: after another 60 seconds;
- after third failure: `failed` + alert.

Policy is editable globally and/or per endpoint.

Permanent errors may end the job without retries: invalid number; forbidden recipient; unsupported content; auth error; endpoint disabled.

Temporary errors are retried: transport unavailable; timeout to acceptance; network congestion; temporary GSM failure; rate limit; session reconnecting.

## 11. Inbound pipeline

Required steps:

1. Validate callback source.
2. Create correlation ID.
3. Save raw payload.
4. Deduplicate.
5. Identify account and endpoint.
6. Normalise number.
7. Normalise type/content.
8. Download attachments.
9. Assemble SMS if needed.
10. Save message/conversation.
11. Create canonical event.
12. Fan-out to all destinations.
13. Save each delivery result.

Callback response: UMG must not return HTTP success before completing a durable DB transaction. After commit it returns transport-specific success as quickly as possible. Further webhook/email/Telegram deliveries happen asynchronously.

## 12. Multipart SMS

### 12.1. Goal

The external system must receive one complete SMS, not a separate workflow run for each segment.

### 12.2. Assembly modes

**Mode A — UDH/structured** — used when callback or vendor DB/API provides concatenation reference, total parts, part sequence, PDU/UDH metadata. Grouping key: `endpoint + sender + concatenation_reference`. Message is closed when all `total_parts` are received.

**Mode B — heuristic** — used only when structured data is missing. Defaults: group key `endpoint_id + sender_e164`; inactivity window 8 seconds; configurable range 2–30 seconds; max assembly lifetime 30 seconds; max parts 20; order by `received_at` then internal sequence; each new part extends the inactivity timer; after timer close one message is created; if loss/anomaly detected — status `incomplete`.

### 12.3. Fan-out behaviour

Default: raw parts are not sent externally; destination receives only final assembled message; technical event `sms.part.received` is available only if explicitly enabled; final event has one stable `message_id`.

## 13. Outbound pipeline

### 13.1. FIFO and rate limiting

Jobs for one endpoint are processed FIFO.

- SMS default: 1 send per 5 seconds.
- WhatsApp default: 1 message per second.
- Signal default: 1 message per second.

Values are editable in UI. Rate limiter must not lose jobs. Manual test send uses the same queue as API.

### 13.2. Scheduled send

API MUST support `scheduled_at`. Time accepted as ISO 8601 with timezone, stored UTC. Can be cancelled before dispatch begins. UI SHOULD have "Send later".

### 13.3. Idempotency

External API MUST support header:

```http
Idempotency-Key: <client-generated-unique-key>
```

Rules: same key + same request → return same result/message_id; same key + different request → HTTP `409 IDEMPOTENCY_CONFLICT`; default retention 7 days; key scoped to global API token.

## 14. Single external API

### 14.1. Authorisation

```http
Authorization: Bearer <GLOBAL_API_TOKEN>
```

Single active global token. Cryptographically secure generation. Hash stored in DB. UI allows viewing metadata, copying a new token at generation time, and revoking the old one. Transport credentials are not the external API token.

### 14.2. Main endpoints

**Messages**

- `POST /api/v1/messages`
- `GET /api/v1/messages`
- `GET /api/v1/messages/{id}`
- `POST /api/v1/messages/{id}/retry`

## 18. Alert engine

### 18.1. Model

Alert is a stateful incident: `open`, `acknowledged`, `resolved`. The same incident must not create an endless stream of duplicate notifications.

### 18.2. Fingerprint

Example: `event_type + account_id + endpoint_id + error_class`.

### 18.3. Default alert rules

| Event | Severity | Condition |
|---|---|---|
| Channel disconnected | critical | state persists > 120 s |
| Channel degraded | warning | 3 consecutive health failures |
| Message final failed | warning | all allowed attempts exhausted |
| Message unknown | warning | cannot determine if sent |
| Low balance | warning | balance crossed threshold downward |
| Balance parse failed | warning | parser did not yield confident result |
| Webhook DLQ | warning | event undelivered after all attempts |
| Queue backlog | warning | queue exceeded configurable threshold |
| Storage low | critical | free space below threshold |
| PostgreSQL/Redis unavailable | critical | readiness failure |
| Adapter recovered | info | previous incident resolved |

### 18.4. Low-balance deduplication

First alert when threshold is crossed; repeat no more than once per 24 hours while balance is low; `sim.balance.recovered` when balance is above threshold again; new low-balance incident possible only after recovery. All intervals configurable.

## 22. USSD and SIM balance

### 22.1. SIM settings

Per SIM: operator; subscriber type; USSD request; schedule; timezone; timeout; retry count; parser profile; expected currency; low-balance threshold; target balance; recommended top-up rule; alert destinations; webhook destinations; selected payload fields; top-up URL template.

### 22.2. Schedule

Support interval, cron and manual check. Default: once per day at configurable time. USSD check must not conflict with SMS job: per-endpoint distributed lock; USSD runs only when endpoint has no active send job; timeout releases lock; no more than one active USSD per endpoint.

### 22.3. Parser pipeline

Raw USSD → encoding cleanup → whitespace normalisation → ordered deterministic rules → numeric validation → LLM fallback if enabled → confidence gate → balance reading → threshold evaluation → event/alert/webhook.

### 22.4. Deterministic rules

Parser profile supports ordered rules with regex, required phrases, excluded phrases, named capture groups `amount`/`currency`/`debt`, decimal separators `,` and `.`, positive/negative transforms, conditional mapping.

### 22.5. LLM fallback

Disabled by default until provider configured. Runs only if deterministic parser fails. OpenAI-compatible endpoint, supports local Ollama/OpenAI-compatible server, strict JSON schema, no tools, no arbitrary system access, default timeout 10 s, max one request per USSD check. Confidence >= 0.85, currency matches profile, amount in configured range, JSON valid, result does not contradict deterministic guard phrases. If validation fails: balance not updated, status `needs_review`, raw response saved, `sim.ussd.failed`/parser alert created.

### 22.6. Low-balance logic

`is_low = is_debt OR amount < threshold`. Event includes SIM, balance, top-up URL.

### 22.7. Top-up URL

UMG does not process payment. Configurable URL template with placeholders `{phone}`, `{phone_e164}`, `{phone_national}`, `{amount}`, `{operator}`, `{endpoint_id}`. If no universal deep link, alert contains number, amount, copy button, operator/payment page URL and optional n8n webhook for custom logic.

## 28. Queues, outbox and reliability

Queue names: `message.send`, `message.status.poll`, `event.dispatch`, `webhook.deliver`, `alert.deliver`, `media.fetch`, `media.cleanup`, `ussd.check`, `health.check`, `reconciliation`, `dead-letter.replay`.

Transactional outbox: critical events first written to PostgreSQL in one transaction with the business entity. Outbox dispatcher reads unpublished records, enqueues, sets `published_at`, is idempotent, has reconciliation.

After Redis loss/restart, reconciliation finds messages in `queued/dispatching` without active job and re-enqueues; finds pending outbox; finds scheduled jobs; does not create duplicate send thanks to locks/idempotency.

Job locks: distributed lock per message; per-endpoint send lock for SMS; per-endpoint USSD lock; lease/heartbeat; stale lock recovery.

DLQ stores: kind; source entity; payload snapshot; error; stack/cause; attempts; first/last failure; next/manual action. UI allows inspect, replay, discard with reason, bulk replay MAY.

## 29. Security

### 29.1. Access

UI available only from LAN/VPN. Single local admin. Password hash: Argon2id. Secure, HttpOnly, SameSite cookie. CSRF protection. Session idle timeout configurable, default 12 hours. Login rate limit. Account lockout after repeated failures with timed release. No 2FA.

### 29.2. First run

Bootstrap admin via one-time environment variables or setup wizard; after creation env password is not used; global API token generated in UI; telemetry disabled; last admin cannot be deleted.

### 29.3. Secret storage

Encrypt: transport credentials; webhook secrets; SMTP password; Telegram token; LLM API key; UnoAPI auth tokens; vendor credentials. Do not log.

### 29.4. Network isolation

Host-exposed: reverse proxy/UI/API; UDP 44444 only in `goip_vendor_embedded`/native mode and only for GoIP IP. Not exposed: PostgreSQL; Redis; UnoAPI; Signal API; vendor HTTP; internal callback routes.

### 29.5. SSRF

Webhook URL may be local, so blanket block of private IPs is forbidden. Instead: admin-controlled allowlist; block cloud metadata ranges; DNS re-resolution check; configurable allowed schemes `http/https`; no `file://`, `gopher://`, unix sockets; timeout/body limit; redirect policy configurable, default no cross-host redirects.

### 29.6. Audit

Log: login/logout; password change; API token generate/revoke; channel/account/endpoint create/update/delete; routing changes; destination changes; alert rule changes; parser changes; retention changes; manual retry/replay; manual USSD; secret replacement without saving plaintext; admin acknowledge/resolve alert.

## 35. Migration from existing SMS Server

### 35.1. Principle

### 35.3. Rollback

## 40. Code requirements

- TypeScript strict.
- No `any` without justified comment.
- Adapter contracts do not depend on specific vendor payload.
- Raw payload stored separately from normalised object.
- Business logic not placed in controllers.
- External calls have timeout, cancellation and typed errors.
- Retry not implemented via `setTimeout` in process memory.
- No unbounded in-memory queues.
- No direct Docker socket.
- No shell command injection.
- No plaintext credentials.
- No hard-coded channel IDs.
- No `latest` production images.
- Database queries paginated.
- UI forms have server-side validation.
- Time comparisons in UTC.
- Phone parsing uses E.164 library, not homemade regex.
- Advanced template is sandboxed.
- All public API changes versioned.
- Generated code/artifacts not edited manually.

## 46. End result of the project

After release 1.0 the administrator must have one internal web service where they can:

- add the GoIP SMS Server and four SIMs;
- add several WhatsApp numbers;
- add several Signal numbers;
- test any endpoint;
- see all history and statuses;
- assemble multipart SMS;
- route inbound/status/health/balance events;
- send one event to multiple destinations;
- use a single API;
- receive alerts;
- control balance/USSD;
- see health of the whole system;
- restore from backup;
- gradually retire the old GoIP UI/server without a risky single cut-over.

Key property: the web UI is the primary management place, and transport components are interchangeable technical executors hidden behind the single UMG model.
