# Посібник оператора UMG

**Unified Messaging Gateway (UMG)** — внутрішній єдиний шлюз для SMS
(GoIP/DBLtek), WhatsApp та Signal. Доступний лише у локальній мережі або
через VPN. Увесь інтерфейс українською.

Типова адреса: `http://<сервер>:8083/`.

---

## 1. Встановлення

Потрібні: Docker та Docker Compose на сервері.

```bash
# 1. Скопіюйте приклад середовища
cp .env.example .env

# 2. ОБОВ'ЯЗКОВО замініть усі значення change-me-* на сильні випадкові секрети:
#    ADMIN_BOOTSTRAP_PASSWORD, SESSION_SECRET, COOKIE_SECRET
nano .env

# 3. Права на файл із секретами
chmod 600 .env

# 4. Запуск
docker compose up -d

# 5. Перевірка стану
docker compose ps
curl http://localhost:8083/api/v1/health/ready
```

Коли всі контейнери `healthy`, відкрийте в браузері
`http://<сервер>:8083/`.

---

## 2. Перший вхід

1. Відкрийте сторінку входу.
2. Логін: `admin`.
3. Пароль: значення `ADMIN_BOOTSTRAP_PASSWORD` із `.env`.

Після першого входу система створює адміністратора, і пароль із `.env`
**більше не використовується** — його можна прибрати з файлу.

Сесія діє 12 годин без активності; після цього потрібен повторний вхід.

## 3. Зміна пароля

1. Увійдіть як `admin`.
2. Відкрийте налаштування профілю.
3. Вкажіть поточний пароль і двічі новий (довгий випадковий).
4. Збережіть. Дія фіксується в журналі аудиту.

Якщо пароль втрачено — аварійне скидання виконується лише як операційна
команда на сервері (не через UI), див. розділ «Типові проблеми».

## 4. Створення API-токена

API-токен потрібен зовнішнім системам (n8n, скрипти) для відправки
повідомлень через `POST /api/v1/messages`.

1. Увійдіть як адміністратор.
2. Відкрийте сторінку **«API-токени»**.
3. Натисніть **«Згенерувати токен»**, за потреби вкажіть назву
   (наприклад, `n8n-integration`).
4. **Скопіюйте токен одразу** — він показується лише один раз. Далі в
   системі зберігається тільки хеш.
5. Старий токен після переходу клієнтів на новий відкличте кнопкою
   **«Відкликати»**.

Використання:

```http
Authorization: Bearer <ВАШ_ТОКЕН>
```

## 5. Додавання каналів

Сторінка **«Канали»** — керування транспортними акаунтами та їхніми
endpoint-ами.

1. **Створіть акаунт**: вкажіть тип (`mock`, `sms`, `whatsapp`, `signal`),
   адаптер, назву та конфігурацію. Секретні дані (паролі, токени
   транспорту) шифруються при збереженні.
2. **Додайте endpoint** до акаунта: підпис, зовнішній ID лінії/номера,
   телефон у форматі E.164 (`+380…`).
3. За потреби **вимикайте/вмикайте** акаунт чи endpoint, або видаляйте їх.

Усі дії з каналами фіксуються в журналі аудиту.

> Для швидкої перевірки без реального обладнання використовуйте вбудований
> канал `mock` — він створюється автоматично.

## 6. Відправка тестового повідомлення

Через API (потрібен токен з розділу 4):

```bash
curl -X POST http://<сервер>:8083/api/v1/messages \
  -H "Authorization: Bearer <ТОКЕН>" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: test-0001" \
  -d '{
    "channel": "mock",
    "to": "+380671234567",
    "type": "text",
    "content": { "text": "Тестове повідомлення" }
  }'
```

Відповідь:

```json
{ "id": "…", "status": "queued", "scheduled_at": null, "created_at": "…" }
```

- `Idempotency-Key` захищає від дублів: повторний запит із тим самим ключем
  поверне вже створене повідомлення.
- Worker доставляє до 3 спроб: одразу, через 60 с, ще через 60 с.
- Того самого результату можна досягти кнопкою відправки на сторінці
  повідомлень у UI (mock-канал).

Повна перевірка системи — smoke test з репозиторію:

```bash
cd /srv/umg
export ADMIN_BOOTSTRAP_PASSWORD=$(grep ADMIN_BOOTSTRAP_PASSWORD .env | cut -d= -f2)
python3 tests/smoke-test.py
```

## 7. Перегляд історії

- Сторінка **«Повідомлення»** — список від новіших до старіших із
  серверною пагінацією та пошуком.
- Картка повідомлення містить: поточний статус, всі **спроби** відправки
  (час, результат, помилку адаптера) та повну **історію статусів**
  (`queued → dispatching → sent → delivered` або `failed`).
- Журнал **аудиту** — хто і коли змінював канали, токени, правила.

## 8. Маршрутизація та вебхуки

> Блок маршрутизації додається у Milestone 1; опис відповідає цільовому
> стану.

**Як це працює.** Кожна подія (наприклад, `message.received`,
`message.sent`, `channel.degraded`) потрапляє в рушій маршрутизації.
**Правила маршрутизації** фільтрують події за типом, каналом, акаунтом,
endpoint-ом, напрямком і критичністю — і спрямовують їх одночасно в кілька
**призначень**: HTTP-вебхук (наприклад, n8n), email, Telegram або
внутрішній журнал.

**Налаштування:**

1. Створіть призначення (вебхук із секретом підпису / SMTP / Telegram-бот).
2. Створіть правило, оберіть фільтри та призначення.
3. Скористайтеся кнопкою **«Тест»** біля призначення, щоб надіслати
   тестову подію.

**Підпис вебхука:** кожен POST містить заголовки `X-UMG-Event-Id`,
`X-UMG-Timestamp`, `X-UMG-Attempt` і `X-UMG-Signature: sha256=<hex>`.
Підпис — `HMAC-SHA256(секрет, timestamp + "." + тіло)`. Перевіряйте його на
боці приймача.

**Повтори та DLQ:** вебхук повторюється за розкладом 0 / 60 / 300 / 900 /
3600 с. Після 5-ї невдачі доставка переходить у **мертві листи**
(`dead_lettered`), створюється алерт. Невдалу доставку можна
**повторити вручну** (replay) зі сторінки доставок — подія та сама,
доставка нова.

## 9. Типові проблеми

| Проблема | Що робити |
|---|---|
| Не відкривається UI | `docker compose ps`; перевірте `reverse-proxy`: `docker compose logs reverse-proxy` |
| 401 на вході | Перевірте логін/пароль. Після кількох невдалих спроб можливе тимчасове блокування — зачекайте кілька хвилин |
| Забули пароль адміна | Аварійне скидання на сервері: зупиніть API, задайте новий `ADMIN_BOOTSTRAP_PASSWORD`, видаліть запис адміна з `admin_users`, запустіть — адмін створиться заново. Далі змініть пароль через UI |
| Повідомлення «висить» у `queued` | Перевірте worker: `docker compose logs umg-worker`; стан Redis/PostgreSQL. Див. `docs/runbooks/queue-recovery.md` |
| Повідомлення `failed` | Відкрийте картку: спроби покажуть помилку адаптера. Канал не перемикається автоматично — виправте причину й надішліть нове |
| Токен втрачено | Відкличте старий і згенеруйте новий — відновити старий неможливо |
| Вебхук у DLQ | Сторінка доставок: перегляньте код/фрагмент відповіді приймача, виправте його й натисніть «Повторити» |
| Диск заповнюється | Перевірте томи медіа та журнали; налаштуйте ретенцію вкладень |

Деталі: `docs/runbooks/` — channel-down, queue-recovery, backup-restore.
