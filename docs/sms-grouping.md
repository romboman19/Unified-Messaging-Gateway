# Приблизне групування вхідних GoIP SMS

Старі GoIP можуть передавати текст без UDH/SAR — спільного номера повідомлення,
кількості частин і номера частини. Для такого входу UMG може збирати SMS за
відправником, SIM і часом надходження. Це евристика: два окремі SMS поспіль можуть
об’єднатися, а запізніла частина — залишитися окремо. Порядок оператора та повноту
повідомлення без цих даних визначити неможливо.

## Увімкнення

Після застосування міграції та оновлення API, worker і web відкрийте **Канали →
потрібна SIM GoIP → Групувати вхідні SMS приблизно → Зберегти групування**.

За замовчуванням групування вимкнене. Типові параметри:

- пауза після останньої нової частини: **25 секунд**;
- максимум від першої частини: **90 секунд**;
- технічна межа: 100 частин у групі.

Налаштування застосовуються до нових груп. Вимкнення закриває поточну групу при
наступному SMS або після вже встановленого таймера. Очікування стосується всіх
вхідних текстових SMS вибраної SIM, включно з короткими кодами.
Інші адаптери й вихідні повідомлення працюють як раніше.

API: `PATCH /api/v1/endpoints/:id` із сесією адміністратора:

```json
{
  "config": {
    "smsGrouping": {
      "enabled": true,
      "idleSeconds": 25,
      "maxSeconds": 90
    }
  }
}
```

Пауза: ціле число 5–120; максимум: від паузи до 300 секунд.
PATCH об’єднує верхні ключі config із поточними значеннями. Оновлення балансу
також змінює лише власні ключі, щоб не стерти паралельно збережене групування.

## Зберігання та пересилання

Кожен оригінал одразу записується в `sms_parts`: текст, сирий payload,
час від SMS Server, час запису UMG та локальна позиція. Група має статус
`assembling` і відображає поточний текст. Позиція означає порядок обробки UMG,
а не номер частини, наданий оператором.

Таймери зберігаються в PostgreSQL та використовують його годинник. Worker перевіряє
прострочені групи щосекунди; після простою завершує їх при запуску. Блокування
на SIM + відправника серіалізує паралельні callbacks. Повтор частини не подовжує
очікування. Завершення групи, подія `message.received` і запис outbox виконуються
в одній транзакції. Маршрутизація бачить лише завершений текст. Під час простою чи
навантаження фактичне пересилання може відбутися пізніше за встановлений максимум.

Група з кількох частин має `metadataJson.smsGrouping.approximate=true` і
`partCount`; ці дані також є в `data.message.metadata` події. Статус
`delivered` тут означає завершення прийому UMG, а не підтвердження повноти SMS.
Пізня частина створює нову групу і не змінює вже створену подію пересилання.

Ідентифікатор GoIP тепер включає хеш лінії, відправника, початкової часової мітки
та тексту. Різні фрагменти в одну секунду не відкидаються. Повністю однакові
payload із тією самою міткою неможливо відрізнити від повторної доставки — вони
вважаються дублем. Якщо мітка відсутня або не розбирається, UMG зберігає кожне
надходження; у цьому випадку повтори можливі. Точні повтори старих записів
перевіряються за старим ID і текстом. Уже втрачені старим кодом частини не відновлюються.

## Ручне виправлення

У **Повідомленнях** розгорніть групу. Видно всі оригінальні частини; після завершення
очікування можна змінити їхній порядок або розділити на окремі SMS. Виправлення
змінюють журнал і фіксуються в аудиті. Уже створені події й доставки залишаються
незмінними, повторного надсилання немає. Ідентифікатори оригіналів залишаються
для дедуплікації навіть після розділення.

Старі SMS автоматично не перегруповуються.

## Оновлення й перевірка

Міграція: `20260926000000_sms_grouping` (нові nullable-поля і таблиця).
Застосуйте її перед запуском нового API/worker. Під час переходу замініть усі старі
worker: одночасний запуск старого та нового обробника може дати різну дедуплікацію.
Увімкніть групування потрібних SIM після оновлення.

Збірка з кореня репозиторію:

```sh
npm ci
npm run db:generate
npm run build --workspace=packages/contracts --workspace=packages/database --workspace=packages/channel-sdk --workspace=packages/adapters
npm run build --workspace=apps/api --workspace=apps/worker --workspace=apps/web
npm run test:sms
```

Без `SMS_TEST_DATABASE_URL` запускаються лише тести адаптера й параметрів.
Для інтеграційних тестів потрібна окрема PostgreSQL-база з назвою `umg_sms_test`.
Тести створюють і видаляють тільки свої записи; робочу базу використовувати не слід.

```sh
export SMS_TEST_DATABASE_URL='postgresql://postgres:postgres@127.0.0.1:5432/umg_sms_test'
DATABASE_URL="$SMS_TEST_DATABASE_URL" npx prisma migrate deploy --schema packages/database/prisma/schema.prisma
npm run test:sms
```

CI виконує ті самі перевірки з PostgreSQL 16. Перевіряються одночасні callbacks,
повтори, відновлення буфера, межі часу, ізоляція SIM/відправників, rollback при
помилці outbox та ручне виправлення без повторного пересилання.
